# Workflow discovery notes

- The user wants rock-solid communication between the Relay server and Relay client, with lower latency.
- The user confirmed “Relay client” means the Relay daemon. The workflow concerns backend ↔ Daemon Node communication.
- The user confirmed a continuous runtime loop: detect interruptions, reconnect automatically when safe, replay pending messages, and surface failures it cannot resolve.
- During temporary transport outages, active agent runs should continue; the daemon retains output and results for replay. Lost contact alone must not trigger duplicate execution.
- Healthy-connection latency target: p95 ≤ 1 second for backend durable command commit → daemon receipt, and daemon output capture → backend durable acceptance. Network/load conditions remain to be specified.
- Temporary-outage recovery target: p95 ≤ 5 seconds after the backend is reachable and accepting authenticated requests, to resume successful command polling and receive the first pending-event replay acknowledgement when events are pending. This does not bound total backlog drain time.
- Pending output and completion/failure reports must survive daemon crashes/restarts and Computer reboots while local storage remains intact. Retain reports durably before transmission and replay until backend durable acceptance. Automatic restart of interrupted agent execution is not decided.
- Under report-storage pressure, preserving pending reports takes priority over continuing execution: stop new admission and safely stop affected runs before exhaustion, reserve final-report space, and surface the problem rather than silently discard output.
- Confirmed configurable report-storage defaults per daemon: 1 GiB shared across runs; stop new admission at 80%; safely stop affected active runs at 90%; reserve the final 10% for shutdown/final reports; resume admission below 50% after recovery.
- Human escalation: after 60 seconds of continuous communication failure, or immediately on credential rejection or storage protection activation. One incident brief per Computer in Relay notifications, updated through recovery rather than one notice per retry; include affected runs, retained reports, recovery attempts, required action, and diagnostics link.
- Accepted initial synthetic transport test profile: 100 connected daemons, up to 3 active runs per daemon, 10 KiB/s output per run, 100 ms network RTT; no paid model calls. Hardware, bandwidth, topology, sample sizes, and faults remain to be specified.
- During backlog replay, stop/cancel commands, heartbeats, and completion/failure reports take priority over old output. Preserve per-run output order. An offline stop remains pending until exit evidence confirms execution stopped.
- Acceptance requires automated faults: dropped requests/acknowledgements, duplicates, backend/daemon restart, Computer reboot, missed command notifications, storage pressure, credential rejection, and offline cancellation. Assert no retry-caused duplicate execution, no lost durably retained reports, no false completion, and recovery or an actionable incident.
- After restart, ambiguous prior execution must remain reserved and must not be automatically rerun. Gather available durable/process/exit evidence before requesting human reconciliation with a decision-ready brief.
- Transient network/server failures retry indefinitely while the daemon runs, using bounded request timeouts and jittered backoff. Unacknowledged reports have no age-based expiry; storage-pressure policy still applies. Permanent rejections require an actionable incident rather than endless retries.
- Permanently rejected reports are retained in quarantine with rejection reason and identifiers, count against the shared budget, and do not block unrelated traffic. Do not claim delivery or skip a rejected sequence within that run. A proven duplicate already durably accepted is acknowledged, not quarantined.
- The user confirmed hardening the existing authenticated HTTP command-long-poll and event-upload transport first; a replacement requires measured evidence that the agreed targets cannot be met.
- Q1–Q17 are settled in `workflows/server-client-reliability.md`. The user confirmed the consolidated operational and verification defaults in Q17. The workflow specification is complete; implementation and live external actions remain outside this specification session.
- Repository terminology: the backend is the control plane; a Daemon Node is the execution-plane runtime on a Computer; the web client is a separate browser surface.
- Use “transport” or “communication” for this topic: “Connection” already means authorization to an external service in `CONTEXT.md`.
